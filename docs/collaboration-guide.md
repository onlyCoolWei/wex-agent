## Purpose

本文定义人类开发者与 Coding Agent 在 Wex Agent 仓库中的协作方式。目标不是限制快速开发，而是让每次开发都围绕明确的业务结果，在不破坏架构边界、既有行为和他人工作的前提下快速交付。

根目录的 [`AGENTS.md`](../AGENTS.md) 是必须执行的规则，本文是其解释、工作流和模板。两者冲突时以 `AGENTS.md` 为准。

开发者快速入口是根目录的 [`CONTRIBUTING.md`](../CONTRIBUTING.md)；本文保留完整治理背景和详细模板，不要求每次任务从头读完。

## 1. 核心原则

### 1.1 功能范围决定修改范围

开始写代码前先把需求压缩成三件事：

- **用户结果**：谁在什么场景下获得什么能力。
- **验收标准**：哪些可观察行为成立才算完成。
- **非目标**：本次明确不处理什么。

文件数量少不等于改动质量高，但任何超出验收标准的修改都必须有明确理由。禁止借功能开发顺手做全局格式化、目录重组、依赖升级或无关重构。

### 1.2 文档是边界，不是事后说明

文档需要回答“为什么这样做”和“什么行为才是正确的”。代码回答“具体如何实现”。当业务行为、公开契约、环境配置或架构决策发生变化时，对应文档属于同一次交付，而不是后续补充项。

### 1.3 自动化守底线，评审关注判断

类型检查、测试、构建和格式检查应交给自动化。评审重点关注业务正确性、边界是否清晰、失败场景、数据兼容和维护成本。不能因为项目暂时缺少某项自动化，就把“没有验证”解释成“没有问题”。

### 1.4 三层质量防线

仓库质量不是靠某一份提示词保证，而是由三层共同承担：

| 层级     | 解决的问题                     | 当前载体                                                 |
| -------- | ------------------------------ | -------------------------------------------------------- |
| 上下文层 | Agent 是否理解产品、术语和架构 | `docs/business/`、`docs/technical/`、`docs/design/`      |
| 执行层   | Agent 修改代码时必须遵守什么   | 根目录 `AGENTS.md` 与必要时的局部规则                    |
| 门禁层   | 违规代码能否被自动挡住         | Prettier、TypeScript、Worker 测试、构建；后续逐步补充 CI |

能由脚本稳定判断的规则，不要只写在文档里。例如公共契约变更应通过类型检查或合约测试发现，格式问题应由 Prettier 发现，依赖方向和密钥泄露则应在具备工具和 CI 基础后加入自动门禁。当前尚未接入的检查必须标为计划，不能写成已经存在的仓库能力。

## 2. 文档体系与单一事实来源

建议按下表维护文档，避免同一规则在多个位置复制后逐渐不一致。

| 文档                      | 回答的问题                         | 维护时机                 |
| ------------------------- | ---------------------------------- | ------------------------ |
| `README.md`               | 项目是什么，如何启动和验证         | 入口、命令或环境要求变化 |
| `AGENTS.md`               | 每次改代码必须遵守什么             | 仓库硬约束变化           |
| `docs/business/README.md` | 产品服务谁、当前能力和业务域是什么 | 产品范围或能力状态变化   |
| `docs/business/*.md`      | 各业务域的规则、不变量和验收是什么 | 对应业务行为变化         |
| `docs/technical/`         | 系统边界和关键技术决策是什么       | 架构边界或技术路线变化   |
| `docs/design/`            | 页面如何交互、有哪些状态和布局     | 功能交互或页面行为变化   |
| `docs/adr/`               | 为什么做出长期且难以逆转的技术选择 | 重要架构决策被确认时     |
| `docs-personal/diary.md`  | 已经交付了什么结果                 | 每次产生仓库文件变更     |

只保留根级 `AGENTS.md`，不要再创建语义重复的 `AGENT.md`。如果某个子目录未来有大量独立约束，可以添加更靠近代码的 `AGENTS.md`，其中只写该目录的增量规则，不复制根规则。

### 文档应写什么

- 稳定的业务概念、状态和不变量。
- 跨模块契约、错误语义和兼容策略。
- 能客观判断完成与否的验收标准。
- 需要维护者理解的取舍和决策原因。

### 文档不应写什么

- 很快过期的逐文件实现过程。
- 从代码中一眼就能看出的类型或函数清单。
- 尚未决定却写成既定事实的设想。
- 与其他文档重复且没有明确归属的规则。

### 业务规则的最小有效结构

高风险业务规则至少写清楚四项：适用条件、不变量、异常场景和代码定位。长篇背景可以帮助理解，但这四项更直接决定 Agent 是否会写出正确实现。代码定位应指向稳定的模块或入口，不要维护一份逐文件实现清单。

## 3. 仓库边界

```text
Browser
  -> apps/web           页面、交互、客户端状态
  -> apps/api           鉴权、校验、业务编排、REST/SSE
       -> packages/database
  -> apps/worker        长任务、Agent Runtime、后台执行
       -> packages/model
       -> packages/sandbox

apps/* <-> packages/contracts   跨进程 DTO 与事件契约
apps/*  -> packages/shared      少量跨域通用能力
```

需要特别守住以下边界：

- Web 不复制 API 或 Worker 已有的契约类型，跨应用类型进入 `packages/contracts`。
- API 不承载长时间 Agent 执行，Worker 不承担对外 HTTP 业务接口。
- SDK、模型供应商、Sandbox 供应商的细节留在适配层，不扩散到业务模块。
- 应用之间不直接互相 import，也不深度导入其他 workspace 的 `src` 文件。
- `packages/shared` 只接收已被多个 workspace 使用且与业务域无关的代码。

## 4. 标准开发流程

### 第一步：建立上下文

1. 阅读根规则、README 和目标功能文档。
2. 检查 `git status --short`，识别并保护他人未提交的改动。
3. 搜索相邻实现、公共类型和已有组件，不凭文件名猜架构。
4. 写出验收标准和非目标；有歧义时先澄清会改变方案的关键点。

### 第二步：设计最小闭环

按照“契约 → 服务端 → 执行端 → UI → 验证”的影响链检查，而不是默认每层都要修改。跨进程契约发生变化时，生产者与消费者必须在同一次变更中同步。数据库变化必须同时考虑 migration、旧数据、回滚或兼容读取。

开始实现前应能回答：

- 权威状态存在哪里？
- 输入在哪里校验，错误如何稳定表达？
- 失败、重试、重复请求和取消会发生什么？
- 是否影响已有数据、API 或配置？
- 最小但足够的验证是什么？

### 第三步：小步实现

- 优先复用既有模式，新增抽象必须解决真实的重复或边界问题。
- 每个修改都能追溯到某条验收标准。
- 不覆盖既有未提交改动，不编辑生成目录，不保留临时日志和调试开关。
- 新依赖、公开契约破坏、migration 和大范围重构都应显式说明理由与风险。

### 第四步：分层验证

先运行最接近改动的检查，再扩大范围：

```bash
# 单 workspace 类型检查
pnpm --filter @wex/web typecheck
pnpm --filter @wex/api typecheck
pnpm --filter @wex/worker typecheck

# Worker 现有自动化测试
pnpm --filter @wex/worker test

# 跨 workspace 影响
pnpm typecheck
pnpm build

# 文档链接、目录边界和模块元信息
pnpm check:docs

# 只检查本次修改的文件，避免顺手改写全仓库
pnpm exec prettier --check <changed-files>
```

用户界面还需手动覆盖与本次功能相关的加载、空数据、错误、禁用和窄屏状态。依赖 Supabase、LiteLLM 或其他外部服务的流程，若因凭据或环境无法验证，交付说明中必须指出未验证部分及原因。

### 第五步：交付前审查

使用 `git diff --check` 和 `git diff --stat` 检查意外空白、修改规模与范围，再逐文件阅读最终 diff。最终说明只需回答：完成了什么、关键文件在哪里、运行了哪些验证、还有什么已知风险。

## 5. 业务功能文档模板

新业务功能或行为明显变化时，应先在 `docs/business/` 建立或更新领域规则，再按需要在 `docs/design/` 或 `docs/technical/` 增加配套文档。短功能可以删减不适用章节，但不要省略目标、规则和验收标准。

- 规则 2：

## 6. 变更风险分级

风险决定验证深度，不由代码行数决定。

| 风险 | 常见变更                                            | 最低要求                                       |
| ---- | --------------------------------------------------- | ---------------------------------------------- |
| 低   | 文案、局部无行为样式、内部文档                      | 格式检查 + diff 审查                           |
| 中   | 单模块行为、局部 API、可逆配置                      | workspace 类型检查 + 聚焦测试/手测             |
| 高   | 公共契约、认证权限、数据库、队列、Runtime、构建配置 | 全量类型检查 + 构建 + 相关测试 + 兼容/回滚说明 |

发现以下信号时应暂停扩大改动并重新确认方案：一次功能触碰多个无关业务域；为了通过检查而放宽类型或删除测试；新增通用层却只有一个调用方；修改配置但无法说明影响范围；文档、实现和验收标准互相矛盾。

## 7. Code Review 检查清单

- 变更是否直接对应已声明的用户结果和验收标准？
- 是否存在与本功能无关的重构、格式化、重命名或依赖变化？
- 模块职责和依赖方向是否仍符合仓库边界？
- 外部输入、权限、错误、日志和敏感信息是否处理正确？
- 合约、数据库、配置和文档是否与实现同步？
- 是否覆盖失败路径、边界条件和已有行为回归？
- 验证记录是否真实，未执行项是否明确披露？

## 8. 推荐的后续自动化

文档能建立共识，但质量底线最终应进入 CI。建议按优先级逐步补齐：

1. 在 CI 中强制执行 `pnpm typecheck`、`pnpm build` 和 `pnpm format:check`。
2. 为 API、Web 的核心业务增加测试入口，并在根脚本统一运行全部测试。
3. 引入 ESLint，重点禁止浮动 Promise、未使用代码和高风险类型逃逸。
4. 配置依赖更新工具和 CODEOWNERS，让高风险目录有明确评审人。
5. 为 PR 增加模板，要求填写范围、验收、验证、数据/契约影响和截图。

在这些自动化真正接入之前，不要把它们写成已经存在的门禁。每增加一项门禁，都应确保本地命令与 CI 命令一致、失败信息可操作、运行时间可接受。
